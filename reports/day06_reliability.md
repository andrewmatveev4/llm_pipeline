# День 6. Надёжность, guardrails и обработка ошибок

## Что сделано
| Механизм | Где | Что делает |
|---|---|---|
| проверка входа | chain.check_input | пустой текст и текст > 4000 символов отсекаются до первого вызова модели |
| классификация ошибок API | llm_client.call_llm | ошибки OpenAI переводятся в LLMAPIError с флагом retryable |
| повтор при сбое API | retry.with_retry | до 3 попыток с паузой 1 с, 2 с; только для retryable ошибок |
| лимит токенов | llm_client.call_llm | max_tokens=1000; обрыв по finish_reason == "length" даёт понятную ошибку |
| лимит длины ответа | chain.compose_answer | ответ > 1500 символов считается провалом шага |
| повтор с подсказкой | chain.run_step | плохой JSON или нет полей: один повтор с текстом ошибки в промпте |
| fallback-ответ | chain.write_answer | если ответ не получен, клиенту честное «передали специалисту», причина в fallback_reason, вердикт на ручную проверку |
| логи | все модули | WARNING на повторы и fallback, ERROR на остановку цепочки, видны попытка, пауза, причина |

Встроенные повторы SDK выключены (max_retries=0), таймаут 30 с вместо 10 минут по умолчанию.

## Какие ошибки API повторяем
| Ошибка | Повтор |
|---|---|
| нет связи, таймаут | да |
| 500, 502, 503 | да |
| 429 rate limit | да |
| 429 insufficient_quota (нет денег) | нет |
| 401 неверный ключ, 400 кривой запрос | нет |

## Негативные сценарии (tests/test_resilience.py, все на фейках, без сети)
1. API недоступен: 3 попытки, цепочка остановилась с понятной причиной
2. неверный ключ: 1 попытка, без повторов
3. текст вместо JSON: повтор с подсказкой, затем остановка
4. нет части ключей: повтор с подсказкой исправил ответ
5. пустой ответ: fallback, цепочка дошла до конца
6. слишком длинный ответ: fallback
7. пустой вход: ни одного вызова модели

Вживую проверены: недоступный API (OPENAI_BASE_URL на закрытый порт), неверный ключ (401),
обрыв по max_tokens=5 (обрывок '{\n  "summary":').

Тестов: 35, прогон 0.25 с.

## Выводы
- Не всякую ошибку API имеет смысл повторять: 429 insufficient_quota приходит тем же классом,
  что и обычный rate limit, различается только по коду
- Повтор при сбое API и повтор при плохом ответе это разные механизмы: первый не меняет запрос
  и ждёт, второй сразу переспрашивает с текстом ошибки
- Fallback не должен скрывать сбой: причина записывается, вердикт «нужна проверка человеком»
- Значение по умолчанию sleep=time.sleep запоминает функцию в момент определения, подмена
  time.sleep в тестах до него не доходит; исправлено получением time.sleep в момент вызова

## Отступления от задания
1. Ошибки вынесены в llm_pipeline/errors.py, чтобы избежать кругового импорта
2. Fallback сделан для шага ответа; при провале шагов 1–3 цепочка останавливается
   с сохранением собранного, т.к. без смысла и категории нечего маршрутизировать
3. Повтор с подсказкой один раз: если модель дважды не справилась, третий раз обычно не помогает
4. Функцию with_retry написал сам по тестам (TDD), остальное по разбору
