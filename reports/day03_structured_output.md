# День 3. Structured output и валидация

## Результат
- Схема LLMOutput (pydantic v2): summary, category, sentiment, key_points (ровно 3), final_answer
- category и sentiment через Literal; список значений один, промпт собирается из схемы (get_args)
- parse_llm_output: строка модели -> LLMOutput или LLMOutputError с понятным сообщением и сырым ответом
- main.py не падает на плохом ответе: ошибка пишется в результат, обработка идёт дальше
- Поля в логике: отчёт по категориям/тональности со всеми значениями схемы (нули включены),
  очередь needs_attention по негативной тональности
- 5 текстов × 2 прогона: 10/10 прошли схему, категории и тональность совпали в обоих прогонах
- Тестов: 15, ветка ошибок покрыта тестами (в реальных прогонах не сработала ни разу)

## Выводы
- Жёсткий контракт (типы, ровно 3 пункта, значения из списка) в схеме: нарушение = ответ отклонён.
  Мягкие лимиты (слова, предложения) остаются метриками в checks.py: 27 слов не повод выбрасывать ответ
- Все три вида поломки (невалидный JSON, нет поля, не тот тип) приходят одним ValidationError;
  различаются по error type, это и даёт понятные сообщения
- Инъекция классифицируется как request: при роутинге (день 4) она пойдёт по ветке
  «выполнить просьбу», нужна отдельная защита
- 01_laptop классифицирован как complaint, хотя заканчивается вопросом: граница question/complaint размыта

## Отступления от задания
1. Своя валидация pydantic вместо нативного structured output OpenAI: работает с любым провайдером
   и позволяет тестировать обработку ошибок
2. Набор категорий выбран мной: question, complaint, request, news, other
3. category и sentiment всегда на английском, иначе правило языка переводило их и ломало Literal
4. Ловится только LLMOutputError; ошибки API и сети не обрабатываются (день 5)
5. response переименован в final_answer; галочка response_ok в checks.py оставлена ради совместимости с кэшем дня 2
6. Роутинга по полям нет (день 4), поля используются для отчёта и очереди внимания
